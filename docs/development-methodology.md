# 用 AI 编程 Agent 交付"可上生产"的 PoC：pi-cli-on-aws 开发复盘与方法论

> 案例：在 AWS CloudShell 中一键安装 pi coding agent，默认使用 Amazon Bedrock（Kimi K3.1），集成 AWS MCP Server、运维 skills 与写操作护栏，作为客户的云上运维助手（成本与用量分析、CloudWatch 可观测、告警配置）。
> 仓库：https://github.com/zhuangyq008/pi-cli-on-aws

---

## 0. 一页纸总结

**交付结果**

| 指标 | 数值 |
|---|---|
| 代码 | 47 个文件，约 5,900 行（含依赖锁文件），单文件最大约 280 行 |
| 自动化测试 | 70 个 bats 单元测试 + 36 个护栏单元测试 + 47 项 CloudShell 端到端检查 |
| 审查 | 1 轮代码审查 + 4 轮安全审查（其中 3 轮对抗式），共发现约 80 项问题，含 7 项 CRITICAL，全部在发布前修复 |
| 发布门禁 | 安全扫描 GATE PASS、敏感信息扫描、全量回归、依赖全部固定版本 + SHA256 |

**方法核心（5 句话）**

1. **先用一手事实定方案**：官方文档、软件包源码、真实 API 实测，不凭印象写代码。
2. **在决策点停下来**：复述理解，把"只有人能做的决定"交给人。
3. **测试先行，并在模拟真实环境的 E2E 中验证**，尤其验证"不该发生的事确实没发生"。
4. **用独立、对抗式、多轮的审查**找自己看不到的问题，直到不再出现高危问题。
5. **安全设计从"拦截已知坏行为"转向"默认无权限 + 可信路径"**。

## 2. 各阶段做法与经验

### 2.1 一手事实调研：把"我以为"变成"我验证过"

**做法**

- 网页文档摘要不全时，直接下载软件包，读其自带的 `docs/` 与编译后的源码（隔离目录中只读，不执行）。
- 对外部服务做真实调用，而不是相信"应该可以"。
- 读工具的真实 schema（例如通过 MCP 客户端列出工具描述与 `readOnlyHint` 注解）。

**本项目实例**

| 假设 | 实测结果 | 对设计的影响 |
|---|---|---|
| "Bedrock 配好模型就能用" | 测试账号中 13 个区域的 Kimi K3.1 Global TPM 配额为 0，即使 `maxTokens=256` 也被限流 | 新增"源区域自动探测"，并区分 Bedrock 源区域与运维区域 |
| "模型目录里 `maxTokens=1048576` 是 bug" | 二分实测：上限约为 `input + maxTokens ≤ 1048576`，pi 已按上下文窗口裁剪 | **避免了一次错误的"修复"** |
| "MCP 的 `--read-only` 可以做安全控制" | 只读模式会隐藏 `run_script`——唯一能调用 AWS API 的工具 | 安全控制必须在客户端（pi 扩展）实现 |
| "扩展拦截不到 codemode 的嵌套调用" | 源码注释明确：嵌套调用同样经过 `tool_call` 钩子 | 无需额外处理该绕过路径 |

> **经验**：每个会影响架构的假设，都值得一个 5 分钟的最小实验。本项目最关键的设计（区域探测、客户端护栏）都来自实测，而不是文档。

### 2.2 尽早复述理解，把决定权交给人

**教训**：调研加实现做了大量工作后，用户中途打断："你再复述下我让你做的是什么"。这说明复述应该更早——**在可行性清楚之后、写大量代码之前**。

**做法**：一段话说明"我的理解 / 计划 / 已发现的关键事实"，再给 2~4 个选择题，每题带推荐默认值。

| 应该由人决定 | 可以由 AI 给默认值 |
|---|---|
| 产品形态（官方工具 + 预配置，还是 fork） | 目录结构、模块拆分 |
| 安全策略（写操作逐次确认 / 默认只读 / 不拦截） | 测试框架、脚本语言 |
| 预装范围、分发方式（GitHub / S3） | 依赖版本固定方式 |
| 推送、发布等对外操作 | 区域自动探测等有明确最优解的细节 |

> 复述后用户补充了真实目标——**给客户做云上运维**——项目因此增加了 AWS MCP、运维 skills 与写操作护栏，价值完全不同。

### 2.3 把目标环境的约束写成清单，逐条对应设计

| CloudShell 约束 | 设计对策 |
|---|---|
| 只有 `$HOME` 持久化，上限 1 GB，且按区域独立 | 全部安装到 `$HOME`；npm / uv 使用临时缓存；精简 Node；总占用约 500 MB |
| 自带 Node 可能低于 pi 要求 | 私有 Node（固定版本 + SHA256），包装器用绝对路径启动，避免 shebang 选中旧版本 |
| 凭证来自容器凭证端点（`AWS_CONTAINER_CREDENTIALS_FULL_URI`） | E2E 中用 localhost 端点模拟同一机制，并禁用 IMDS |
| `AWS_REGION` 等于控制台区域 | 只对 pi 的模型调用改写区域；agent 的 bash 与 MCP 仍使用原区域 |
| 浏览器 OAuth 回调到不了 CloudShell | AWS MCP 选择 SigV4 代理而不是 OAuth |
| 用户有 sudo，同一用户无法做进程隔离 | 安全模型如实写明边界，并把 IAM 作为最终防线 |

### 2.4 TDD 与小模块

**做法**

- Shell 用 bats 测试，TypeScript 护栏用 `node --test`；测试运行在沙箱 `$HOME` 中，`aws`、`curl` 用桩替代，单元测试不访问网络、不调用 AWS。
- **纯函数与副作用分离**：安全判断（分类、策略）都是纯函数，可以穷举测试；pi 钩子只负责执行决策。
- 小文件（最大约 280 行），单一职责。

**测试也会错**：失败时先判断是"测试错"还是"实现错"。

| 测试中的错误 | 教训 |
|---|---|
| 断言在 JSON 事件流里 grep 期望字符串，但事件流会**回显用户 prompt** | 断言要证明"行为发生了"，而不是"字符串出现了"——改为解析最后一条助手消息 |
| 凭证探针用 `AWS_C` 前缀计数，结果匹配到护栏自己导出的 `AWS_CONFIG_FILE` | 探针要精确，失败时先人工复现确认 |
| E2E 断言"运维区域是 us-east-1"通过，但启动器的默认值恰好也是 us-east-1 | **断言要选默认值以外的值**——改用 ap-northeast-1 后才真正证明环境变量被传递 |

**测试抓到的真实 bug**：返回码初始值错误导致选区失败、`set -o pipefail` 下 `find` 失败使卸载脚本静默退出、正则前瞻在参数末尾不匹配等。

### 2.5 环境模拟 E2E：还原"关键差异"，不只跑通 happy path

**模拟要素**：独立 `$HOME`、`AWS_EXECUTION_ENV=CloudShell`、仅通过 localhost 容器凭证端点提供凭证（禁用 IMDS）、PATH 中只有旧版 Node、非 us-east-1 区域。

**覆盖链路**：安装 → Bedrock 对话 → bash 工具区域还原与凭证剥离 → MCP 只读查询 → 写操作在非交互模式被拒绝 → **用 RPC 模式模拟用户点"拒绝"** → doctor → 幂等重装 → 卸载。

**E2E 发现、单元测试发现不了的问题**

| 现象 | 根因 |
|---|---|
| `Invalid RFC-3339 date-time value` | JS SDK 只接受 `Z` 结尾的时间，`aws configure export-credentials` 输出 `+00:00`（模拟器保真度问题） |
| pi 返回 Anthropic 401 | 未检测到 AWS 凭证环境变量时，pi **静默回退**到其他已配置 provider → doctor 增加"实际 provider"校验 |
| `pi -p` 卡住 6 分钟 | stdin 不是终端时 pi 会等待读取 stdin → 脚本中统一 `</dev/null` |
| 卸载失败 | `pipefail` + 备份目录不存在 → 赋值失败 → `set -e` 静默退出 |

> **经验**：E2E 要验证**负向结果**——例如"告警确实没有被创建"：测试主动查询资源，若存在则清理并判定失败。

### 2.6 独立、对抗式、多轮审查

**做法**

- 并行启动独立的审查 agent（安全 / 代码），**只给代码与威胁模型，不给自己的结论**，避免审查者被引导去"确认"已有判断。
- 要求"只报告亲自复现过的问题，并给出具体输入"。
- 威胁模型要写清边界：区分 **(a) AI 正常会写出的命令** 与 **(b) 刻意规避的输入**，否则审查会无限扩大。
- **修复后对新设计重新审查**。

| 轮次 | 类型 | 发现 | 最严重 | 结论 |
|---|---|---|---|---|
| 1 | 安全审查（全仓库） | 18 项 | HIGH × 6（如续行、别名、先写脚本再执行可绕过护栏） | 需要重做护栏 |
| 1 | 代码审查 | 20 项 | HIGH × 4（如 doctor 误报 OK、卸载后用户配置丢失） | 修复 |
| 2 | 对抗式审查（护栏） | 19 种绕过 | CRITICAL × 3（`for ...; do aws ...`、`find -exec aws`、`/usr/bin/env aws`） | **补丁修不完 → 换架构** |
| 3 | 对抗式审查（新架构） | 12 项 | CRITICAL × 4（参数前缀缩写泄露签名请求、`jq env` 泄露凭证、`sort --compress-program=sh`、全角字符绕过） | 加固自动路径 |
| 4 | 发布门禁 | 3 MEDIUM + 6 LOW | 无高危 | GATE PASS |

> **经验**：每一轮都发现了上一轮之后才出现的高危问题。"修完一轮"不等于"安全"，**要审到不再出现高危为止**。

### 2.7 架构收敛：从"拦截坏行为"到"默认无权限"

| 版本 | 设计 | 问题 |
|---|---|---|
| v1 | 用正则 / 分词识别 bash 中的 AWS 写操作 | shell 语法空间无限：循环、子 shell、续行、引号混淆、`find -exec`、先写脚本再执行……19 种绕过 |
| v2 | **bash 默认剥离 AWS 凭证**；只有严格白名单内的只读 `aws` 命令自动带凭证；其余需人工确认 | 漏判的后果从"写入 AWS"变成"命令因无凭证而失败"；但白名单路径本身仍有漏洞 |
| v3 | 自动路径**不执行原文**：用校验后的参数重建命令，**凭证只给 aws 进程**；aws 参数、过滤器选项、重定向目标全部白名单 | 修复 `AWS_PAGER=sh`、参数前缀缩写、`jq env`、`sort --compress-program` 等 |

> **原则**：当"识别坏行为"的空间无限时，改为"**限制能力 + 枚举好行为**"。安全性不再取决于分析器有多聪明，而取决于默认状态有多安全。

### 2.8 发布门禁

- [ ] 安全扫描（独立 agent，输出 GATE: PASS / FAIL，CRITICAL/HIGH 阻断发布）
- [ ] 敏感信息扫描：账号 ID、内部路径、密钥、个人信息（本项目在发布前扫描并清理了文档中的环境专属信息）
- [ ] 全量回归：lint + 单元测试 + E2E，**基于最终代码**重新运行
- [ ] 供应链：所有下载固定版本并校验 SHA256（Node、uv、pi tarball、81 个 Python 依赖、skills 内容清单）
- [ ] README 与代码一致（测试数量、参数、文件布局）
- [ ] 对外操作（推送、上传）前确认目标与权限

## 3. 踩坑清单

| # | 坑 | 现象 | 对策 |
|---|---|---|---|
| 1 | Bedrock 跨区域推理配额按**源区域**计算 | 部分区域 TPM 为 0，任何请求都 `ThrottlingException` | 安装时探测并自动选择有配额的源区域；申请提额 |
| 2 | 模型目录元数据"看起来"有 bug | `maxTokens = contextWindow` | 先二分实测上限，确认无需修改 |
| 3 | provider 静默回退 | 没有 AWS 凭证环境变量时 pi 改用其他 provider | doctor 解析事件流，校验实际 provider |
| 4 | 非交互运行阻塞 | `pi -p` 在非 TTY 下等待 stdin | 一律 `</dev/null` |
| 5 | 凭证时间格式 | JS SDK 不接受 `+00:00` | 模拟器规范化为 `Z` |
| 6 | `set -euo pipefail` | 管道中任一命令失败使赋值失败，脚本静默退出 | `\|\| true` 显式容错，并补针对性测试 |
| 7 | Python venv 不可搬移 | 脚本 shebang 是绝对路径 | 直接在最终位置构建 |
| 8 | 官方只读模式过于粗粒度 | `--read-only` 隐藏唯一的 API 工具 | 客户端按操作分类 |
| 9 | 测试断言被 prompt 回显欺骗 | 失败的调用也"通过" | 解析结构化事件中的助手消息与 stopReason |
| 10 | 断言恰好等于默认值 | 未传递环境变量也"通过" | 使用非默认值做断言 |
| 11 | 文本正则做安全拦截 | 被循环、续行、别名等 19 种写法绕过 | 默认无凭证 + 白名单 |
| 12 | 环境变量可执行命令 | `AWS_PAGER=sh` 把输出当命令执行 | 白名单只允许置空 |
| 13 | CLI 参数前缀缩写 | `--endpoint` 等同 `--endpoint-url`，签名请求被发往外部 | 拒绝危险参数的任何前缀 |
| 14 | Unicode 规范化 | Python 把全角 `ｃall_boto3` 视为 `call_boto3` | 分析前做 NFKC 规范化 |
| 15 | 1 GB `$HOME` | 缓存可能写满磁盘 | 临时缓存 + 预检剩余空间 + 精简安装 |

**跨平台（macOS / Windows）新增的坑**——共同特点：在开发机上不会出现，只有在真实目标系统（或高保真模拟）上才会暴露：

| # | 坑 | 现象 | 对策 |
|---|---|---|---|
| 16 | macOS bash 3.2：空数组 + `set -u` | `"${arr[@]}"` 报 unbound variable | `${arr[@]+"${arr[@]}"}`；用真实 bash 3.2 跑测试 |
| 17 | macOS bash 3.2：`$VAR` 后紧跟中文 | 多字节首字节被并入变量名（`VAR?: unbound variable`） | 一律 `${VAR}`，并加静态检查测试 |
| 18 | Windows PowerShell 5.1 读取无 BOM 的 .ps1 | 按 ANSI 代码页解码，中文字节变成引号，整个脚本语法错误 | .ps1 一律 UTF-8 with BOM，加测试守护 |
| 19 | PowerShell 5.1 输出被重定向时 | 原生命令的 stderr 变成错误记录，`ErrorActionPreference=Stop` 下中断 | 调用原生命令时局部改为 Continue；交互时不要捕获输出（会失去 TTY） |
| 20 | 7z 自解压包（PortableGit）在无桌面会话（SSM / 服务） | 直接退出码 1；系统自带 bsdtar 不支持 LZMA | 改用官方 Inno 安装包 `/VERYSILENT /CURRENTUSER`（无需管理员） |
| 21 | Git Bash 的 MSYS 路径转换 | 参数和环境变量中的 `/tmp/x`、`/dev/null` 传给原生程序时被改写 | 安装路径统一用 `C:/...` 形式；用户参数用 `MSYS2_ARG_CONV_EXCL` 关闭转换 |
| 22 | Git Bash 的 PATH 以 `:` 分隔 | `C:/x:$PATH` 被拆成 `C` 和 `/x` | PATH 条目转换为 `/c/x` |
| 23 | 原生程序输出 CRLF | `$(aws configure get region)` 残留 `\r`，区域校验失败 | 统一经 `_strip_cr` 处理 |
| 24 | Windows 上 Python 忽略 `HOME` | 把 aws 进程的 `HOME` 指向快照目录无效，仍读真实 `~/.aws` | 同时设置 `USERPROFILE` |
| 25 | Windows 路径的多种写法 | `C:\`、`c:/`、`/c/`、`~\`、8.3 短名、`\\?\`、大小写，护栏按字符串比较会漏判 | 统一规范化后比较；用 `realpathSync.native` 展开短名 |
| 26 | npm 全局目录布局、`ln -s` 行为不同 | Windows 上包在 `prefix/node_modules`；MSYS 的 `ln -s` 默认复制整个目录 | 按平台计算路径；Windows 不用符号链接 |
| 27 | 测试环境的网络策略 | default 安全组出站被收紧；VPC 内 STS 接口终端节点只允许 default 安全组 | 测试实例同时加入专用安全组与 default 安全组；报错时显示底层原因而不是"验证失败" |
| 28 | `import.meta.url === \`file://${argv[1]}\``判断是否直接运行 | Windows 上 argv[1] 是 `C:\...`，判断恒为假，脚本静默不执行、退出码 0 | 按文件名判断，并加静态检查禁止该写法 |
| 29 | 路径的"形式"不统一 | Git Bash 中 `readlink -f` 保留输入的 `C:/...` 形式而 `$HOME` 为 `/c/...`，安全检查误判"不在 HOME 下" | 比较前统一转换（`cygpath -u`）并忽略大小写 |
| 30 | schannel 的偶发错误 | `missing close_notify`（curl 错误 56），`--retry` 默认不重试 | Windows 上加 `--retry-all-errors`（内容由 SHA256 兜底） |
| 31 | 用真实模型做护栏 E2E | 模型主动拒绝读取凭证、或按规则"先查后改"因缺权限停下，护栏根本没被触发 | 选模型会照做的受保护操作；断言"未泄漏"与"被拦截"分开；给测试身份补足只读权限 |

## 5. AI Agent 运维工具的安全设计原则

本项目提炼的原则可直接用于客户的 AI 运维方案设计：

1. **默认无权限**：agent 的通用执行环境（bash）默认不带云凭证；需要时显式授予、逐次确认。
2. **可信路径优于可信文本**：自动执行的命令由校验后的参数重建，而不是执行模型给出的原文。
3. **读写分离**：只读操作自动执行以保证效率；写操作、凭证类读取人工确认；非交互模式一律拒绝。
4. **失败即拦截**：静态分析无法确认为只读的调用（动态参数、别名、反射、子进程）一律需要确认。
5. **最小授权范围**：凭证只注入真正需要的进程（aws CLI），管道中的其他程序无凭证。
6. **保护护栏自身**：护栏与配置文件只读；修改受保护路径（配置、扩展、shell 启动文件）需确认。
7. **可审计**：所有需确认操作的决策写审计日志，日志中的密钥自动脱敏。
8. **供应链可验证**：所有组件固定版本并校验哈希。
9. **平台级纵深防御**：使用专用受限 IAM 角色，并用 `aws:ViaAWSMCPService` 等条件键限制经 MCP 发起的操作。
10. **诚实说明边界**：明确哪些风险客户端控制无法消除（例如同一用户拥有 sudo）。

## 6. 人机协作方式

| 环节 | 人 | AI 编程 Agent |
|---|---|---|
| 目标与约束 | 说明业务目标、客户场景 | 复述理解、列出环境约束 |
| 调研 | — | 读文档与源码、做实测、整理事实 |
| 决策 | 选择产品形态、安全策略、分发方式 | 给出选项与推荐默认值 |
| 实现与测试 | 关键节点抽查 | TDD 实现、E2E 模拟、修复 |
| 审查 | — | 编排独立审查 agent、汇总并修复 |
| 发布 | 授权推送 / 发布 | 门禁检查、提交、推送、验证 |

**用到的 harness 能力**

- **并行后台任务**：E2E（约 8 分钟）在后台运行，同时进行审查与修复。
- **独立子 agent**：安全审查、代码审查、对抗式审查各自独立上下文，互不影响判断。
- **结构化提问**：在决策点用选择题让人快速决定（带推荐默认值）。
- **记忆**：把"先复述理解再动手"等反馈记录下来，后续项目直接沿用。
- **门禁规则**：推送前强制安全扫描，由规则文件而不是临时判断来保证。
